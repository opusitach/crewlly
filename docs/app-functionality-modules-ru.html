5. Сквозные сценарии по ролям

5.1 Типичный день owner/manager

  1. Открывает /app и смотрит KPI: сколько на проверке, выручка за сегодня/месяц, активные смены.
  2. Если есть «требует внимания», идет в настройки (касса/команда/роли/чаевые).
  3. В планнере создает/обновляет смены; при необходимости использует bulk.
  4. После завершения смен проверяет процедуры и кассу в verification.
  5. Публикует рабочие дни и завершает review кассовых смен.
  6. Смотрит отчеты и при необходимости запускает payroll run.

5.2 Типичный день worker

  1. Видит ближайшую смену и статус.
  2. Перед стартом проходит OPEN-процедуры, при необходимости делает фото.
  3. Открывает смену; в конце проходит CLOSE-процедуры и закрывает смену.
  4. В табе planner смотрит только свои смены (без редактирования).
  5. В табе money смотрит начисления за период.

6. Полное описание модулей платформы

6.1 Аутентификация, сессия, контекст организации

Что это на человеческом языке

Это вход в систему и выбор “в каком заведении сейчас работаем”. Один пользователь может иметь доступ к нескольким организациям и переключаться между ними без перелогина.

Ключевое поведение

  • Логин/регистрация создают cookie-сессию.
  • При логине берется активная membership (с учетом activeOrganizationId).

Что это для бизнеса

  • Код приглашения для сотрудников.

6.4 Worker onboarding и подключение к заведению

Что это для сотрудника

Сотрудник вводит код, система проверяет валидность приглашения, показывает организацию/должности и завершает присоединение.

Проверки

  • Код должен быть активным, не просроченным, с доступным лимитом uses.
  • Если пользователь уже активный участник организации, возвращается статус ALREADY_MEMBER.
  • При blocked membership присоединение блокируется.

Результат успешного входа

  • Создается/активируется membership worker.
  • Создается/обновляется employee.
  • Пользователь переключается в worker режим, onboardingReady=true.

6.6 Owner dashboard

Человеческое описание

Главный экран владельца: контроль операционки “здесь и сейчас” — что требует внимания, что сейчас в работе и какие деньги/проверки на очереди.

6.9 Роли (positions) и шаблоны правил процедур

Человеческое описание

Для каждой должности задаются правила до/после смены. Это стандартизирует процесс и снижает ошибки.

Что поддерживается

  • Типы правил: CHECKLIST, INPUT, PHOTO, CASH.
  • Привязка к этапу OPEN/CLOSE и к конкретному дню недели или default.
  • Лимит PHOTO правил: не более 10 на этап/контекст.
  • Для CLOSE required фактически всегда true.
  • Изменение шаблонов синхронизирует процедуры в запланированных сменах.

Критичное правило планнера

Для создания/обновления смены у позиции обязателен корректный default ruleset (минимум OPEN и CLOSE правила). Иначе API вернет конфликт.

6.10 Планнер смен — обычный режим (single create/edit)

Что это для пользователя

Планнер — центральный инструмент расписания. Менеджер выбирает день, назначает сотрудника/позицию/время и получает сразу валидированный результат.

Поток

  1. Выбор даты в месяце/неделе.
  2. Заполнение формы смены (сотрудник, позиция, время, перерыв, pay-параметры).
  3. Сохранение: если workday отсутствует, он создается автоматически.
  4. Если есть пересечение по времени — возвращается overlap конфликт.

Важные правила

  • Поддерживаются HH:mm и ISO datetime payload.
  • Ночные смены поддерживаются (end <= start в HH:mm → перенос end на следующий день).
  • Редактирование в UI доступно только для scheduled/conflict.
  • При смене pay-параметров расчетные payroll snapshot-поля инвалидируются и пересчитываются позже.

Конфликты

  • Обычное сохранение без override при overlap возвращает 409 + список конфликтующих интервалов.
  • Статус conflict виден в карточке и подробностях.

API

МетодEndpointНазначение
GET/POST/api/workdaysЧтение/создание рабочих дней.
GET/POST/PUT/DELETE/api/intervalsCRUD смен.
POST/api/workdays/[id]/publishПубликация (дальше день считается reviewed в verification).

6.11 Планнер смен — bulk режим (детально)

Зачем это нужно

Bulk режим ускоряет планирование однотипных смен сразу на много дат. Владелец/менеджер один раз заполняет форму, система создает пакет интервалов.

Как включается

  • В планнере есть переключатель «Массово» (isBulkMode).
  • В этом режиме календарь собирает множественный набор дат (bulkSelectedDates).

Пошаговый поток bulk-create

  1. Включить «Массово».
  2. Выбрать нужные даты в месячном календаре.
  3. Открыть форму и заполнить единые параметры смены.
  4. При сохранении каждая дата проходит цикл: getOrCreateWorkday(date) → createInterval(...).
  5. Для API-create в bulk передается allowConflictStatus: true.

Что означает allowConflictStatus в bulk

  • Пакет не «падает целиком» из-за одного пересечения.
  • Конфликтные элементы могут быть созданы со статусом conflict (вместо полного запрета пакета).

Поведение при ошибках bulk

  • Если не создано ни одной смены: ошибка операции.
  • Если часть создана: частичный успех с сообщением «создано N, ошибок M».
  • Если все создано: единый success toast.

Ограничения bulk

  • В readOnly режиме bulk полностью отключен.
  • Позиция обязана иметь default OPEN/CLOSE ruleset.
  • Пересечения и конфликты по сотруднику все равно фиксируются системой.

API (bulk использует те же endpoint-ы)

МетодEndpointНазначение в bulk

POST/api/intervalsСоздание интервала на каждую дату с allowConflictStatus.

6.12 Исполнение смены: процедуры, open/close, cancel, clock

Что это на практике

Сотрудник не просто “нажимает открыть/закрыть”, а проходит обязательные правила, включая чек-листы, поля, фото и кассовые вводы.

Что поддерживается

  • Загрузка процедур OPEN/CLOSE для конкретной смены.
  • Сохранение ответов всех типов правил.
  • Проверка required и photo-required для cash полей.
  • Force open/close owner-ом (только owner, только с причиной).
  • Cancel shift: только planned/scheduled, обязательно с причиной.
  • Clock-in/out с фото и геопозицией; при clock-out формируется payroll snapshot.

Бизнес-ограничения

  • Открыть нельзя уже открытую/закрытую смену.
  • Закрыть нельзя неоткрытую смену.
  • Если required правила не выполнены, open/close блокируются (кроме owner force).
  • Если CASH правило в workday уже заполнено другой сменой, кассовый блок становится lock/read-only для текущей смены.

API

POST/api/work-intervals/[id]/procedures/answersСохранить ответы по правилам.
POST/api/work-intervals/[id]/openОткрыть смену (валидации required).
POST/api/work-intervals/[id]/closeЗакрыть смену + payroll snapshot + cash/tips sync.
POST/api/work-intervals/[id]/cancelОтменить запланированную смену.

6.13 Касса: настройки полей и формул

Человеческое описание

Модуль определяет “какие данные кассы собираем” и “как считаем итоговые показатели” (в том числе источник чаевых и выручки).

Что настраивается

  • Поля OPEN/CLOSE: required, photo-required, sign, порядок, revenue-basis.
  • Формулы: resultKey/resultLabel/expression/порядок.
  • Метки формул: источник чаевых и источник выручки.

Критичные ограничения

  • Настройку меняет только owner.
  • Хотя бы одно активное поле и хотя бы одна формула обязательны.
  • Не более одной tips-source формулы и одной revenue-source формулы.
  • Запрещено совмещать isTipsSource и isRevenueSource в одной формуле.
  • Revenue-basis поле должно быть CLOSE-полем и только одно.
  • По флагу overwriteExistingSessions можно принудительно пересинхронизировать существующие open/closed сессии.

GET/PUT/api/tips/settingsМетод деления чаевых equal/by_hours.

6.14 Кассовые сессии: open → close → review → owner-edit

Что это для операционки

Кассовая сессия хранит фактические денежные значения дня и подтверждается отдельным review-процессом.

Жизненный цикл

  1. Open: обязательные open-поля и создание snapshot.
  2. Close: обязательные close-поля, валидация, lockVersion-check, пересчет totals.
  3. Review: перевод статуса в reviewed.
  4. Owner-edit: owner правит closed/reviewed; reviewed после правки откатывается в closed.

Ключевые правила

  • Открытие кассы допустимо только в draft workday.
  • Закрытие кассы запрещено в published day.
  • Review только из closed.
  • Добавление receipt запрещено для reviewed.
  • Для конкурентной защиты используется lockVersion в close/review/owner-edit.

API

6.15 Проверка смен и кассы (verification) — детально

Что это на простом языке

Это модуль финального контроля: подтвердить, что рабочие смены закрыты корректно, а кассовые сессии проверены ответственным менеджером/owner.

Вкладки verification

  • Work shifts: завершенные рабочие смены на выбранную дату.
  • Cash sessions: закрытые и проверенные кассовые сессии на дату.
  • Review queue: единая очередь того, что еще не подтверждено.

Критерий «смена проверена»

В текущей модели проверка смены определяется не отдельным флагом интервала, а публикацией рабочего дня: workday.status === "published".
  1. В Work shifts попадают интервалы со статусом completed.
  2. Кнопка «Проверено» вызывает POST /api/workdays/[id]/publish.
  3. После публикации day все completed интервалы этого дня в verification считаются reviewed.

Критерий «кассовая смена проверена»

  1. В Cash sessions видны closed и reviewed.
  2. Кнопка «Проверено» вызывает POST /api/cash/sessions/[id]/review.
  3. Проверенной считается сессия со статусом reviewed.

Логика очереди Review queue

  • Очередь смен: interval.status=completed и day еще не published.
  • Очередь кассы: cashSession.status=closed.
  • Сводный счетчик в owner dashboard берется из /api/verifications/summary.

Drill-down и что проверяется фактически

  • По смене: OPEN/CLOSE правила, фото, чек-листы, input-поля, фактическое время.
  • По кассе: snapshot полей open/close, формулы, чеки (receipts), cash photos из процедур.

6.16 Отчеты и аналитика

Что пользователь получает

Управленческую картину по кассе и людям за период: динамика полей, вычисления формул, предупреждения и детализация начислений сотрудников.

Функции

  • Кассовая сводка: количество сессий, поля open/close, формулы, formulaWarnings/formulaErrors.
  • Проваливание в конкретное поле кассы с историей по датам.
  • Проваливание в конкретную формулу с историей/ошибками.
  • Сводка по каждому сотруднику и карточка его начислений за период.

Важно

  • Перед расчетом отчет может автоматически синхронизировать недостающие cash sessions из процедур.
  • При ошибках формул отчет не падает целиком: возвращаются warnings/errors.

6.17 Payroll

Что это делает

Формирует payroll run за период: зарплата + чаевые по сотрудникам, даже если часть интервалов еще не имела сохраненного payroll snapshot.

Как работает

  • Берутся completed интервалы периода.
  • Для интервалов без расчетных полей выполняется on-the-fly пересчет.
  • Добавляются tip allocations из pools.
  • Формируются payroll items с total payout.

Доступ

  • Создание run: owner/manager.
  • Просмотр payroll items: owner/manager или worker только свои.

API

МетодEndpointНазначение
POST/api/payroll/runsСоздать payroll run за период.
GET/api/payroll/itemsПолучить payroll items.
